# Границы публичного и внутреннего API

Этот документ фиксирует границы до внедрения JWT. Он не меняет существующие
маршруты, а задаёт политику для следующего этапа.

## Единственная публичная точка входа

В production клиент обращается только к API Gateway. Прямое подключение к
`auth-service`, `user-service`, `academic-service`, `schedule-service`,
`content-service`, `notification-service`, `communication-service` и
`news-service` запрещено сетевыми настройками.

## Публичные маршруты без access token

| Маршрут | Назначение |
| --- | --- |
| `GET /` | Информация о gateway |
| `GET /health` | Проверка gateway для оркестратора |
| `POST /api/v1/auth/register` | Регистрация |
| `POST /api/v1/auth/login` | Вход |
| `POST /api/v1/auth/refresh` | Обновление пары токенов |
| `GET` опубликованных новостей | Публичная новостная лента; точный allowlist будет добавлен с JWT |

`/docs`, `/redoc`, `/openapi.json` и `/health/services` разрешены только в
development либо во внутренней административной сети.

## Маршруты с JWT

- `GET /api/v1/auth/me`
- `PATCH /api/v1/auth/change-password`
- `POST /api/v1/auth/logout`
- все пользовательские профили и связи родитель-студент;
- филиалы, направления, учебные планы, модули, группы и участники групп;
- кабинеты, расписание, занятия и посещаемость;
- материалы, домашние задания и работы студентов;
- уведомления и пользовательские настройки;
- чаты, сообщения, вложения, прочтение и WebSocket;
- создание, редактирование, публикация и модерация новостей.

## Внутренние маршруты

RPC через RabbitMQ и будущие HTTP-endpoint между сервисами не публикуются
через общий proxy. Для них будет применяться отдельная service-to-service
аутентификация.

## Правила владения

JWT-проверка сама по себе недостаточна. После её добавления сервис обязан
проверять роль и владение ресурсом. Поля `user_id`, `student_id`, `sender_id`,
`created_by` и аналогичные нельзя принимать как доказательство личности из
query/body — действующий пользователь определяется по access token.
